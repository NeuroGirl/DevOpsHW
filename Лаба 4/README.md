# Лабораторная работа №4: Окружения и CI/CD (Это база, это base)

## 1 Часть

Сначала намеренно делаем плохо - файл bad_cicd.yml

Bad practices (плохой CI/CD):

1. Секреты захардкожены в YAML (`DEPLOY_PASSWORD`, `API_TOKEN`) и печатаются в логах (`echo "Password:"`), которые
   часто доступны многим участникам/системам, это прямой риск утечки информации. Конечно прям так
   врядли кто-то додумается в реальности сделать, но как пример сойдет.
2. Нет ограничения деплоя по ветке, он рабоает на любой push - можно случайно задеплоить незавершенный код из
   feature-ветки, плюс будет много бессмысленных деплоев, запускаемых, например, из-за изменений в README (то
   есть никак не влияющих на сам проект).
3. Используется устаревший action (`actions/checkout@v3` вместо более актуального `v4`).
   Старые версии могут не содержать важных исправлений безопасности и багфиксов.
4. Не выбрана конкретная версия образа, используется `ubuntu-latest`. Пайплайн становится нестабильным,
   потому что окружение может внезапно измениться с обновлением версии образа.
5. Игнорирование провала этапов (`continue-on-error: true`). В чем пойнт CI/CD если мы игнорируем провалы этапов?
   Вот в этом и ошибка - даже при проблемном коммите мы все равно деплоим изменения, поздравляю с сломанным проектом
   и потраченными компанией милиардами.
6. Нет ограничений времени, из-за чего возможно зависание джобы. Зависшие задачи тормозят работу команды.

Теперь исправляем то, что сами намеренно зафорчмачили - файл good_cicd.yml

Исправления:

1. Секреты не хардкодятся в коде и не выводятся в логи = +безопасноть.
3. Деплой только для `main` = + контроль релизов и экономия ресурсов и времени.
4. Используется не устаревшая (но и не latest) `actions/checkout@v4`, зафиксирована версия образа `ubuntu-22.04` = +стабильность.
6. Этап тестов обязателен: при провале пайплайн останавливается и в CI/CD снова появляется смысл = +качество.
7. Добавлены ограничения времени для всех job = +++ экономия ресурсов и времени.
